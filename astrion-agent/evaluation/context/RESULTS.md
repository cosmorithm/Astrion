# Context Eval v1：首次小样本记录

实验时间：2026-11-01。模型：`deepseek-flash`。实验基于固定合成历史，调用真实模型完成上下文构造及无工具的一次回答；并未运行完整科研 Agent。初始代码位于提交 `8652b7e` 的工作树，工作树当时有未提交修改；本次运行的模型客户端含已有的本地修改，不能声称运行源码全部固定。每组请求和回复保存在本机 JSON 中，数据文件 SHA-256 保存在报告中。

## 80% 触发水位：3 题 × 3 组

样例 C01、C02、C03，每个组合运行一次。对压缩组，B = 初始消息字符 × 1.25，构造后目标 = 0.5B。append 不设压缩目标，仅作为完整历史参考。

| 方案 | 回答值精确匹配 | 成功构建且达目标 | 构建 token | 回答 token | 总 token | 累计耗时（秒） |
|---|---:|---:|---:|---:|---:|---:|
| append | 3/3 | 不适用 | 0 | 4,976 | 4,976 | 7.96 |
| legacy | 3/3 | 3/3 | 7,790 | 1,824 | 9,614 | 29.28 |
| SS | 3/3 | **0/3** | 17,989 | 4,883 | 22,872 | 110.04 |

**SS 三组都未成功构建。** 模型已逐条生成 SS，但合起来的目录超过了该次字符预算，报 `context_directory_exceeds_budget`。随后测试程序使用未替换的完整上下文回答，因此表中 SS 的 3/3 **不是 SS 重构成功后的正确率**，不能用于宣称与旧压缩效果持平。三次 SS 构建结果累计约 4,207、4,390、3,861 字符（不包括目录 JSON 元数据），而对应预算约 3,645、3,630、3,591 字符。目标约 80 token 只是提示，程序当前不强制模型遵守。

在 C01 的加长历史上另外运行一组**较紧压力预算**（0.5B 约为初始字符数的 40%）：SS 目录进入了规划，规划选了三个关键 Step，但候选视图仍未通过目标检查，返回 `context_protected_content_exceeds_target`。这个错误名称不能单独证明是受保护内容导致的：当前检查也覆盖候选过大或没有缩短的情况。失败后保留完整上下文，该组答案仍然不能当作 SS 重构的有效结果。该加长样例与 C01 是同一事实集合，不能算独立题目。

## 严格本地 token 契约后的多轮试验（2026-11-01）

三道样例分别做首次回答和两次追问；同一构建结果用于后续追加，追问不调用工具或重新构建。新版以本地 DeepSeek tokenizer 对固定 JSON 消息/工具表示计数，初始水位为本地预算的约 80%，重构目标为 50%。实际服务端可能采用不同的隐藏模板，数字不构成服务端绝对 token 保证。

| 方案 | 首答正确 | 两次追问正确 | 达到本地重构目标 | 已知总 token | 累计耗时 |
|---|---:|---:|---:|---:|---:|
| 完整追加 | 3/3 | 6/6 | 不适用 | 15,159 | 21.76 秒 |
| 原有压缩 | 3/3 | 6/6 | 3/3 | 13,655 | 44.57 秒 |
| 严格 SS | 3/3 | 6/6 | 3/3 | 28,636 | 122.26 秒 |

三次 SS 构建共生成 24 条 SS，按本地 tokenizer 检查均不超过 80 token；每次重构后的本地 token 数分别为 777、741、727，目标分别为 998、994、991。发送前记录的各压缩组模型请求本地计数均在各自 B 内。三题一次、合成历史和无工具续答只能说明这次流程，不能说明更广泛的事实召回或成本优势。SS 总用量仍高于另外两组，且顺序摘要调用带来较高时延。

早期多轮报告的 C03 追问将“有效成分质量”写成“溶液质量”，有歧义；模型回答信息不足并非必然错误。该原始结果及 `followups_v1_ambiguous.json` 均保留。表内使用修正后的追问重跑，不覆盖旧报告。

- 本机[严格预算多轮报告](../../eval_reports/context_strict_token_v4_multiturn_reviewed.md)、[完整 JSON](../../eval_reports/context_strict_token_v4_multiturn.json)。
- 本次运行发生在代码尚未提交时，报告保存运行时源码哈希；随后补充了缓存中间档位退档等改动，因此不能把报告等同于对最终提交所有分支的验证。
- 摘要生成、Planner、回查和每次追加均有成本；本实验未测试 Agent 实际多轮执行中的自动重构、工具重读、并发子 Agent 或语义裁判。

随后使用当时的 token 契约与少选实现另做一次 C01 严格 SS 与两次追问冒烟：首次及两次追问均正确；重构本地计数 945/998，SS 最大 64 本地 token，已知用量 10,026 token。本次整个实现过程包含中间实验及完整 Agent 冒烟，已知累计用量 163,250 token；至少一次传输重试用量未知，且完整 Agent 冒烟未保存底层重试诊断。中间旧版和新版本报告均保留，不将它们混合计算通过率。

## 真实 Agent Loop 的历史回查试验（2026-11-01）

使用固定的合成长历史，先直接调用旧压缩或 SS 构造器，再把一个新问题交给真实 `agent.run`，允许调用本 Agent 的历史搜索、重读与证据工具。三题的目标分别在早、中、晚 Step；每组最多 10 轮。各组共享本地输入预算 B，但旧压缩使用自己的字符目标，三次都没有达到本地 0.5B，因此不能当成**同输出预算**的严格胜负。提问阶段人为放宽字符水位，本地 token 水位仍能触发重构；这不是工作台默认配置的原样表现。

| 样例 | 方案 | 构建后本地 token / 目标 | 提问前答案字面可见 | 结果 | 已知 token |
|---|---|---:|---|---|---:|
| L01 早期 | 旧压缩 | 3417 / 3356 | 是 | 答对 148；非遗漏后找回 | 10,751 |
| L01 早期 | SS | 2570 / 3356 | 否 | 后续重构恢复摘要，随后读原文并答对 148 | 41,015 |
| L02 中期 | 旧压缩 | 3469 / 3355 | 是 | 超本地输入预算，发送前被拦截 | 26,246 |
| L02 中期 | SS | 2248 / 3355 | 是 | DeepSeek 工具调用协议 HTTP 400 | 36,761 |
| L03 后期 | 旧压缩 | 3462 / 3350 | 是 | DeepSeek 工具调用协议 HTTP 400 | 41,009 |
| L03 后期 | SS | 2228 / 3350 | 否 | 尚未找到目标，DeepSeek 工具调用协议 HTTP 400 | 33,260 |

L01/SS 最初视图不含 `148`；Agent 前两轮搜索或读取的工具结果也未给出该数。之后一次自动重构把 Step 1 的 SS 放入决策视图，Agent 才搜索 `148`、读取 Step 1 原文、固定证据并回答。它展示了“**重构恢复摘要 → 工具重读**”，并不能证明完全靠工具独立发现数字。

三次 HTTP 400 的上游响应均包含 `reasoning_content` 和工具调用，而随后失败请求的 assistant 工具调用历史缺少该字段；错误文本明确要求思考模式回传 `reasoning_content`。当时 `Memory.add_assistant` 会清理该字段。三组未完成，应计未完成，不能当作答错。L02/旧压缩的本地计数为 7681，超过 B=6711，程序在发送前拦截；实验人为放宽了字符水位，不能直接断言默认工作台也会按同样轨迹失败。

六组已报告的 token 合计 **189,042**，并有失败请求和未追踪的 Agent 内部重试，实际用量可能更高；逐组耗时及完整事件见本机[复核报告](../../eval_reports/context_live_recall_v1_reviewed.md)和[原始 JSON](../../eval_reports/context_live_recall_v1.json)。首次运行时工作树存在未提交改动，且脚本随后增加了重试记录、档案快照和首现顺序判定；旧 JSON 未被覆盖，不能把后续脚本改进追溯到这次运行。样例少、语义裁判缺失、预算目标不等，无法据此得出总体胜负或科研任务成功率。

## DeepSeek 工具调用协议修复后的重测（2026-11-02）

沿用上述三组曾遇到 HTTP 400 的题目及策略；每组一次，其他实验条件不变，未覆盖原报告。先保存并按来源回传模型实际返回的 `reasoning_content`。第一次 L02/SS 重测仍在中途重构后返回 HTTP 400：原因是程序构造的 assistant 摘要没有该字段；对程序生成的摘要明确发送空字符串后，单独重放该失败请求获得成功。此空值不用于补造旧模型响应。

| 样例 | 方案 | 结果 | 本地拦截 | 已知 token |
|---|---|---|---|---:|
| L02 | SS | 完成，答案 `0.0005` 正确；目标值首先在工具结果中出现 | 无 | 49,614 |
| L03 | 旧压缩 | 未完成；发生多次真实工具调用 | 7,245 > 6,701 | 44,528 |
| L03 | SS | 未完成；发生多次真实工具调用 | 9,687 > 6,701 | 53,314 |

两组 L03 均在压缩重构未能继续缩小时，被发送前的本地预算检查阻止，未观察到原 HTTP 400；不能算作答错，也不能宣称任务成功。现有轨迹没有保存最后一次重构失败的具体原因，不能据此断定原因。实验人为放宽字符水位，不代表默认工作台配置；本地 tokenizer 数量也不是服务端计费或窗口的绝对保证。

另外真实流式客户端完成一次两轮工具调用，工具返回 `713`、最终回答 `713`，已报告 1,953 token；这只是协议冒烟，不代表科研质量。第一次失败的中间版 L02 重测已知 32,279 token；重放其失败请求已知 3,246 token。本次各阶段已报告总计 184,934 token；至少有一次 HTTP 400，失败请求的用量未知，且 L03 组脚本对未完成组保守标记用量不完整。两份最终报告及中间报告和完整轨迹保存在本机 `eval_reports/context_recall_reasoning_v2_l02_ss.*`、`context_recall_reasoning_v2_l03.*`、`context_recall_reasoning_l02_ss.*`，这些文件不会随 Git 推送。运行时工作树存在其他未提交修改，原始 JSON 保存源码哈希，不能把整次运行等同于干净提交的验证。
